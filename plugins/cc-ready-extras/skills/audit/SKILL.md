# 전체 점검

프로젝트를 영역별로 점검하고 점수표를 낸다. **진단만 한다. 코드, 설정, 문서를 고치지 않는다.** 점검 중에 코드가 바뀌면 점수를 비교할 수 없게 된다.

- 인자 없음: 10개 영역 전부
- `--quick`: 실행이나 브라우저가 필요 없는 영역만(코드 구조, 주석과 문서, 테스트, 보안). 빠르고 싸다
- 영역 이름을 주면 그 영역만 (예: `디자인 사용성`)

영역마다 무엇을 보고 어떻게 점수를 내는지는 [areas.md](areas.md)에 있다. 시작 전에 읽는다.

## 0. 준비

1. 프로젝트를 파악한다: README, CLAUDE.md(가져온 AGENTS.md 포함), package.json 같은 설정, 폴더 구조. 화면이 있는 프로젝트인지(웹, 앱, 데스크톱), 화면이 없는 프로젝트인지(라이브러리, CLI, 서버) 정한다.
2. 화면이 없으면 디자인, 사용성, 접근성, 화면 문구는 "해당 없음"으로 두고 점수에서 뺀다.
3. 실행 방법을 찾는다(개발 서버, 빌드, 미리보기). 화면을 보려면 브라우저 도구가 있어야 한다(Playwright MCP, Chrome DevTools MCP, agent-browser 등). 없으면 화면 영역은 코드만 읽고 매기고, 그 영역에 "화면은 확인 못 함"을 단다.
4. 직전 점검을 찾는다: `.audit/` 폴더에서 이름이 가장 늦은 `*-audit.json`.
5. 무엇을 어떤 방법으로 볼지 세 줄 안으로 알리고 바로 시작한다. 예: "화면 있는 웹 프로젝트. 10개 영역, 브라우저는 Playwright MCP로 확인. 직전 점검 2026-11-14."

## 1. 영역별 점검

영역은 서로 독립이라 하위 에이전트로 나눠 동시에 돌려도 된다(하위 에이전트를 쓸 수 있을 때). 나눈다면 묶음 셋 정도로:

- 화면: 기능, 디자인, 사용성, 접근성, 화면 문구
- 코드: 코드 구조와 리팩터링 거리, 주석과 문서, 테스트
- 위험: 보안, 성능

하위 에이전트에게는 그 묶음의 areas.md 내용과 아래 "지적 하나의 모양"만 넘긴다. 내 짐작이나 기대하는 결론은 넘기지 않는다.

지적 하나의 모양:

```
- 영역: 사용성
- 등급: P0 | P1 | P2
- 어디: 파일:줄, 또는 화면 주소와 동작
- 무엇: 한 문장
- 근거: 실행 출력, 스크린샷, 코드 인용 중 직접 본 것
- 고치는 법: 한 문장
```

등급:

| 등급 | 뜻 |
|---|---|
| P0 | 지금 사용자가 막히거나, 데이터, 돈, 보안을 잃는다 |
| P1 | 자주 걸리거나, 고치지 않으면 곧 문제가 된다 |
| P2 | 다듬을 거리. 있으면 좋다 |

## 2. 반증

P0와 P1은 받아들이기 전에 한 번 깨 본다.

- `verifier` 에이전트가 있으면 지적마다 "이 지적은 사실이다"를 넘긴다. 없으면 직접 반대 증거를 찾는다(재현해 보기, 호출부 끝까지 읽기, 문서 확인).
- 결론이 "거짓"이나 "모름"이면 그 지적은 뺀다. 뺀 수만 보고서에 적는다.
- 직접 본 근거가 없는 지적은 등급과 상관없이 뺀다.

## 3. 점수

점수는 남은 지적으로 계산한다. 느낌으로 매기지 않는다. 그래야 다음 점검과 비교할 수 있다.

```
영역 점수 = 10 - (P0 × 3) - (P1 × 1) - (P2 × 0.3), 0 아래는 0, 소수 첫째 자리 반올림
```

- 영역마다 areas.md의 "꼭 볼 것"을 하나도 확인하지 못했으면 점수를 내지 않고 "확인 못 함"으로 둔다.
- 총점 = 점수가 있는 영역의 평균 × 10 (100점 만점). 몇 개 영역으로 냈는지 함께 적는다.
- P2가 많아 점수가 깎이는 것은 정상이다. P2는 한 영역에서 5개까지만 센다(그 이상은 목록에만 남긴다).

## 4. 직전과 비교

직전 점검이 있으면 붙인다. 같은 화면과 같은 동작, 같은 파일과 같은 문제면 표현이 달라도 같은 지적으로 묶는다.

| 구분 | 뜻 |
|---|---|
| 되풀이 | 직전에도 나온 지적. 고친 방식부터 다시 본다 |
| 새로 나옴 | 이번에 처음 나온 지적. 직전 뒤에 고친 자리에서 생겼으면 표시한다 |
| 사라짐 | 직전엔 있고 이번엔 없음. 두 번 연속 안 나와야 해결로 본다 |

- 점수를 직전과 나란히 놓는다.
- 1~2점 변화는 점검 흔들림일 수 있어 진척이라고 말하지 않는다. 판단은 되풀이 목록이 줄었는지로 한다. 같은 영역이 두 번 연속 오르거나 내리면 그때 변화로 본다.

## 5. 저장과 보고

`.audit/` 폴더에 두 파일을 남긴다. 이름 앞은 UTC 시각이다(예: `20261121T0930Z`).

- `<시각>-audit.md`: 사람이 읽는 보고서 (아래 모양)
- `<시각>-audit.json`: 다음 비교용. `{ "date", "mode", "areas": { "<영역>": { "score", "findings": [{ "grade", "where", "what" }] } }, "total" }`

`.audit/`을 git에 넣을지는 사용자에게 한 번 묻는다. 팀이면 넣는 편이 비교에 좋다.

보고서 모양:

```
## 점수표 (총점 N/100, 영역 N개)
| 영역 | 점수 | 직전 | P0 | P1 | P2 | 한 줄 |
| 기능 | 8.0 | 7.0 | 0 | 2 | 0 | 가입 뒤 첫 화면이 빈 채로 뜬다 |
...

## 먼저 고칠 것 (P0, P1)
1. [보안 P0] 파일:줄 — 무엇. 고치는 법.
...

## 직전과 비교
(되풀이, 새로 나옴, 사라짐 표)

## 다듬을 거리 (P2)
(영역별 목록)

## 고치러 가기
- 리팩터링 거리: /cc-ready-extras:refactor 대상
- 버그: /cc-ready-extras:fix-issue 증상
- 낡은 문서와 주석: /cc-ready-extras:update-docs
- 그 밖의 것: /cc-ready:plan-feature 로 계획부터

## 이번에 못 본 것
(확인 못 한 영역과 이유, 반증에서 뺀 지적 수)
```

## 규칙

- 코드를 고치지 않는다. 고치자고 하면 보고를 마친 뒤 위 "고치러 가기"의 스킬로 넘긴다.
- 직접 보지 않은 것을 점수에 넣지 않는다. 실행하지 못했으면 "확인 못 함"이라고 쓴다.
- 지적을 늘리는 것이 성과가 아니다. 문제가 없으면 없다고 쓴다.
- 취향은 지적이 아니다. 디자인과 문구는 그 프로젝트의 규칙(DESIGN.md, CLAUDE.md, 디자인 시스템)과 areas.md 기준에 어긋날 때만 지적한다.
- 무겁다. 전체 점검은 하위 에이전트를 여럿 쓰고 시간이 걸린다. 작은 수정마다 다시 돌리지 말고, 몇 개를 묶어 고친 뒤 돌린다. 코드만 바꿨으면 `--quick`.
